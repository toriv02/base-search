# Поисковый движок по Wikipedia (DuckDB + Kotlin)

Консольное/десктопное приложение (Swing) для полнотекстового поиска по дампам Wikipedia.

## Структура основных файлов

```text
src/main/kotlin/
├── Main.kt                     # точка входа, запуск Swing-приложения
├── ui/
│   └── SearchUI.kt             # интерфейс поиска и отрисовка результатов
├── query/
│   ├── Query.kt                # AST запроса: Term, And, Or, Not
│   ├── QueryParser.kt          # разбор строки запроса в AST
│   └── QueryEvaluator.kt       # вычисление AST по posting-листам
├── index/
│   ├── SegmentedIndex.kt       # чтение сегментов индекса с диска
│   ├── IndexBuilder.kt         # построение и сброс сегментов на диск
│   └── Hash.kt                 # вычисление 128-битного хэша терма
└── storage/
    ├── DiskDocumentStore.kt    # получение полных документов по id
    └── Document.kt             # модель документа
```

## Как исполняется запрос

Процесс обработки поискового запроса происходит в несколько этапов:

1. **Ввод и парсинг:** После ввода пользователем строки через `SearchUI`. После чего строка передаётся в класс `QueryParser`, который в свою очередь разбирает её в абстрактное синтаксическое дерево, по средствам использования класса `Query`.
2. **Оценка (Evaluation):** `QueryEvaluator` проходит по дереву `Query`.
   - Для `Query.Term` вызывается `index.postingList(term)`;
   - Для `Query.And` вычисляется пересечение списков документов;
   - Для `Query.Or` вычисляется объединение;
   - Для `Query.Not` вычисляется разность с множеством всех документов.
3. **Чтение постинг-листов:** `SegmentedIndex` для каждого терма вычисляет 128-битный хэш, находит его в словаре сегмента и читает соответствующий массив ID документов из `postings.bin`.
4. **Вывод:** `QueryEvaluator` возвращает отсортированный массив id документов. `SearchUI` берет первые 20 id, запрашивает полные данные документов через `DiskDocumentStore` и отрисовывает карточки.

## Где хранится Posting List

Posting List хранится **на диске** в бинарном виде в папке `index/`.

Индекс разбит на сегменты (`seg_0`, `seg_1`, ...). Каждый сегмент содержит:
* `dict.bin` - словарь. Хранит 128-битные хэши термов (`h1`, `h2`), смещение (`offset`) и количество документов (`count`). Словарь отсортирован по хэшам для быстрого бинарного поиска.
* `postings.bin` - сами постинг-листы. Это непрерывный файл, в котором записаны 4-байтовые целые числа (ID документов), отсортированные по возрастанию.
* `meta.txt` - метаданные сегмента (количество документов).

Во время *построения* индекса постинг-листы временно хранятся в оперативной памяти в `HashMap<String, IntArrayList>`, но при достижении лимита (250 000 документов) сбрасываются на диск (`flushSegment`).
